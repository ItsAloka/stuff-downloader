Stuff Downloader - third-party licences
=======================================

Licence audit for plan.md section 8.3. Audited 2026-09-22 from the installed package metadata
of every pinned environment, the bundled tool builds (tools/SOURCES.txt) and the frozen onedir
build (dist/StuffDownloader). Nothing has been distributed. This file records what would apply
if the app ever is.

tests/unit/test_third_party_licenses.py keeps the package sections below in step with the lock
files: a package added, removed or re-pinned without updating this file fails the suite.


1. How the pieces are combined (the licensing boundary)
--------------------------------------------------------

There are three separate kinds of program. None is linked into another.

  a. The GUI: StuffDownloader.exe, a PyInstaller onedir build of src/stuff_downloader with
     PyQt6. PyInstaller excludes every engine package (packaging/StuffDownloader.spec,
     ENGINE_EXCLUDES), and tests/unit/test_third_party_licenses.py fails if the GUI package imports
     one. Checked 2026-09-22: dist/StuffDownloader/_internal contains no yt_dlp, gallery_dl,
     spotdl, mutagen or curl_cffi.

  b. The engine workers: one virtualenv per engine under the app-managed CPython runtime
     (%LOCALAPPDATA%\StuffDownloader\runtime). The GUI starts each worker as a child process and
     talks to it only through JSON lines on stdin and stdout (core/runner.py). Each worker imports
     its own engine and the project's stuff_downloader_worker package.

  c. The command-line tools: ffmpeg.exe, ffprobe.exe and deno.exe, run as child processes.

Conclusions:
  - Keeping the processes separate means PyQt6 (GPL-3.0-only) never has to share one program with
    gallery-dl (GPL-2.0-only). That is the incompatible pair plan 8.3 warned about, and the design
    avoids it.
  - Each worker environment, however, is one combined program: the engine plus
    stuff_downloader_worker plus its dependencies. See section 5 for the obligations this creates.

5. Findings - to resolve before any distribution
-------------------------------------------------

F1  RESOLVED - the project's own code is under the MIT License.
    The owner chose MIT for the repository's original source code. The text is in LICENSE,
    and pyproject.toml declares license = {text = "MIT"} with the MIT classifier. MIT is
    compatible with the GPLv2-only gallery-dl worker process and lets the PyQt6-linked
    StuffDownloader.exe be conveyed under GPLv3 as a whole, with its source.
    This does not clear any obligation below.

F2  RESOLVED - the spotDL dependencies spotapi and spotipyfree do ship licences.
    An earlier audit read only the METADATA License field and missed the licence files.
    The pinned wheels each contain dist-info/licenses/LICENSE:
      spotapi 1.2.8       GNU General Public License version 3 (full text). METADATA has no
                          License field and names no "or later" option, so treat it as GPL-3.0.
      spotipyfree 1.9.14  MIT License, "Copyright (c) <2026> <Tzur Soffer>". The METADATA
                          License field carries only that copyright line.
    Obligation: spotapi adds to F5. Distributing the spotDL environment means conveying spotapi
    under GPLv3: ship its licence text and its corresponding source (or a written offer). The
    MIT notice for spotipyfree must ship with it (F6). Both LICENSE files are staged by the
    payload builder into licences\spotapi-1.2.8 and licences\spotipyfree-1.9.14.
    Current build scope: personal use on the owner's machine only; the installer is not shared.

F3  OBLIGATION - FFmpeg is GPLv3.
    Shipping ffmpeg.exe or ffprobe.exe requires shipping this licence text and offering the
    complete corresponding source for that exact build (FFmpeg plus every statically linked
    library) for three years, or shipping the source alongside.
    Alternative: switch to an LGPL build (gyan.dev or BtbN "lgpl" builds) and check that no
    preset needs x264 or x265.

F4  NOTE - gallery-dl is GPL-2.0-only and requests is Apache-2.0.
    The FSF considers Apache-2.0 incompatible with GPLv2-only. This combination is upstream's
    own, since gallery-dl depends on requests itself, and this project does not create it.
    Shipping the gallery-dl environment still means shipping that combination.
    The M6 installer does ship it: the payload carries the hash-pinned gallery-dl and requests
    wheels in runtime-setup\, and setup-runtime installs them offline into the gallerydl
    environment on the user's machine. That is distribution of both packages, not a fetch from
    PyPI, so the GPLv2/Apache-2.0 incompatibility applies to the installer as a whole.
    Resolution: acceptable only for the owner's personal, local build. Before the installer is
    shared, either get legal advice on this combination or stop bundling the gallery-dl wheels
    and have the installer fetch them by hash from PyPI instead.

F5  OBLIGATION - the spotDL environment is effectively GPLv3.
    pykakasi (GPL-3.0-or-later), spotapi (GPL-3.0), mutagen and unidecode (GPL-2.0-or-later)
    load into one process with spotDL (MIT) and the worker code, so that process is governed by
    GPLv3. This is compatible with F1's permissive choice. Any distribution of that environment must include
    the licence texts and a source offer.

F6  OBLIGATION - notices for every other component.
    MIT, BSD, ISC, Apache-2.0, MPL-2.0 and PSF all require their licence text and copyright
    notices to ship with the binaries. The M6 installer should copy each package's
    dist-info/licenses files into a licenses\ folder next to this file.

The boundary claim in plan 8.3 holds. PyQt6 and gallery-dl never share a process. It was
checked against the build output above and is guarded by test_third_party_licenses.py.
